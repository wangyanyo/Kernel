## 1. 摘要
当前代码的进程生命周期机制与Linux有所不同，因此实现Linux的标准进程生命周期管理；
**验收标准**：修改用户程序，通过fork、exec、exit、wait等系统调用维护进程生命周期，用户程序运行无问题；

## 2. 背景与问题
**我们为什么要这样做：**
我们的最终目的是，该内核可以直接替换Ubuntu的Linux内核正常使用，因此就需要保证系统调用的接口与行为与Linux保持一致；
**目前的问题：**
在当前代码中，通过一个system系统调用同时完成了创建新进程和执行程序两个动作，这个和Linux的标准处理方式由所不同。\
**Linux内核的标准方案：**
在Linux内核中，进程的生命周期是这样的：
1. 当前进程先通过fork系统调用复制出一个新的进程；
2. 执行exec系统调用运行新的程序，当前进程是新进程的父进程；
3. 新进程执行结束后，会执行exit系统调用，内核会回收该进程的所有资源，但是不会释放struct task_struct实例；
4. 直到父进程执行wait系统调用，确认子进程已经死亡并顺便回收struct task_struct实例；

## 3. 目标与非目标
### 目标
- 我们要重构当前的代码，实现Linux内核中标准的进程的层次关系和生命周期管理；
### 非目标
- 只实现进程生命周期管理机制，及其相关的科技树，不考虑其它的机制，不要陷入到Linux源代码的细节中；

## 整体方案设计
### 4.1 《深入Linux内核架构》笔记
进程有五种状态，运行、等待、睡眠、终止、僵尸；
1. 当调度器决定从该进程收回CPU资源时，该进程的状态会从“运行”变为“等待”；
2. 当调度器为该进程分配CPU时间后，该进程的状态会从“等待”变为“运行”；
3. 如果进程必须等待事件，则其状态从“运行”变为“睡眠”；
4. 睡眠进程等待的事件发生后，其状态从”睡眠“变为“等待”；
5. 进程终止执行后，进程状态变为“终止”；

但是还有一个特殊的僵尸状态，即子进程终止执行，发起exit系统调用，内核回收该进程的所有资源，但没有释放对应的task_struct实例，
这就是一个僵尸进程，父进程发起wait4系统调用可以确认子进程终止执行，并顺便释放子进程的task_struct实例；
也就是说，如果父进程不调用wait4系统调用的话，僵尸进程会稳定的存在于系统中，引入常驻内存问题；

Linux内核涉及进程和程序的所有算法都围绕一个名为task_struct的数据结构建立，task_struct是Linux内核最核心的数据结构之一；
我们只关注与我们当前项目相关的结构成员：
```
struct task_struct {
        volatile long state;    // 进程状态
        void *stack;            // 内核栈，内部还有一个thread_info
        
        long exit_state;                // 进程退出状态
        int exit_code;                  // 进程退出码

        unsigned did_exec:1;

        pid_t pid;

        // 进程间层次关系
        struct task_struct *parent;
        struct list_head children;
        struct list_head sibling;
};
```

在Linux内核中，有三种复制进程的方式：
1. fork: 重量级复制，它建立了父进程的一个完整副本，然后作为一个子进程执行；这样做有很多缺点，需要申请大量内存而且耗时很长，更关键的是，通过
   fork创建出的新进程大概率要执行一个新的程序，因此之前复制的大部分内容都失效了，尤其是复制了一整个内存空间都浪费了；但是Linux内核为fork
   引入了写时复制机制，大大减少了fork所需的时间和内存；
2. vfork: vfork创建了一个父进程的轻量级副本，执行vfork后，父进程会进入睡眠状态，直到子进程执行新程序；
3. clone: clone是fork的一个变体，用于创建线程，可以传入各种定制化的参数；

由于fork引入了写时复制技术，因此vfork在速度上不再有优势，更何况还有对父进程的限制，因此现在应该避免使用vfork；

在调用fork时，内核通常会对父进程的每个内存页，都为子进程创建一个副本，这有两个负面影响：
- 使用了大量内存
- 复制耗费了很长时间

但是这样做的收益甚微，创建子进程无非两种情况：
1、子进程和父进程并行执行，但是一个技术事实是，进程通常只使用内存页的一小部分，大部分复制的内存页子进程都不会访问；
2、子进程立即执行新的程序，复制的内存页将全部被丢弃；
也就是说，fork系统调用的复制是完全多余的，造成了内存和时间上的浪费；
因此引入的写时复制技术，父子进程可以随意读共享内存页，但是如果要写内存页，会触发中断并复制该内存页内容，然后再执行写操作，该过程父子进程都不感知；

执行进程复制的函数是do_fork函数，该函数的定义如下：
```
long do_fork(unsigned long clone_flag,
             unsigned long stack_start,
             struct pt_regs* regs,
             unsigned long stack_size,
             int __user *parent_tidptr,
             int __user *child_tidptr);
```
该函数的参数含义如下：
- clone_flag是一个标志集合，用来指定复制过程的一些属性。最低字节指定了在子进程终止时发给父进程的信号，其余高位字节保存了各种常数；
- stack_start是用户状态下栈的起始地址；
- regs是一个指向寄存器集合的指针，其中以原始形式保存了调用参数；struct pt_regs是一个特定于体系结构的数据结构；
- stack_size是用户状态下栈的大小；
- parent_tidptr和child_tidptr我们不关注；

为了避免后期大规模重构，项目的上层接口定义与Linux内核保持一致；
clone_flag一般传SIGCHLD，代表子进程终止后会向父进程传SIGCHLD信号，便于父进程执行wait4系统调用；
如果do_fork成功，会返回新进程的pid作为系统调用的结果返回，否则返回错误码；

sys_clone用于创建线程，它也会调用do_fork函数，但是其传入的参数是用户指定的，而sys_fork传给do_fork的参数则是静态的；
sys_clone传入用户指定的clone_flag，通过标志位来决定是与父进程共享资源，还是创建父进程资源的副本；

不论是创建进程还是创建线程，最终都会调用do_fork函数，该函数做了什么呢？
do_fork
	-> copy_process
	-> 确定PID
	-> 初始化vfork的完成处理程序和ptrace标志
	-> wake_up_new_task
	-> 是否设置了CLONE_VFORK标志？-> wait_for_completion
do_fork从copy_process开始，生成进程，根据标志决定如何重用父进程的数据；
然后就是确认PID，如果涉及命名空间，这部分的处理就比较复杂；如果不涉及，就直接生成一个新的PID即可；
Ptrace相关的处理不涉及；
通过wake_up_new_task函数唤醒新进程，即把进程放进就绪队列中；
如果当前是vfork，则调用wait_for_completion，父进程进入睡眠状态，子进程退出或者执行新程序后，父进程才会被唤醒，我们的项目不涉及vfork

do_fork的大部分工作都是copy_process完成的：
copy_process
	-> 检查标志
	-> dup_task_struct
	-> 检查资源限制
	-> 初始化task_struct
	-> sched_fork
	-> 复制/共享进程的各个部分
		-> copy_semundo
		-> copy_files
		-> copy_fs
		-> copy_sighand
		-> copy_signal
		-> copy_mm
		-> copy_namespace
		-> copy_thread
	-> 设置各个ID、进程关系、等等

首先是检查标志，内核会捕获所有明显矛盾的标志组合，并返回错误
如果没有矛盾的标志组合，则执行dup_task_struct复制父进程的task_struct实例，复制好的task_struct实例除了stack指针外，其余所有成员都与父进程相同；
在Linux内核中，内核栈中存储了thread_info的实例，用于保存所有特定于处理器的底层信息；
```
union thread_union {
	struct thread_info thread_info;
	unsigned long stack[THREAD_SIZE/sizeof(long)];
};
```
内核栈的大小一般是8KB，也就是连续的两个页帧；在栈顶存储了thread_info数据结构：
```
struct thread_info {
	struct task_struct	*task;		/* main task structure */
	struct exec_domain	*exec_domain;	/* execution domain */
	__u32			flags;		/* low level flags */
	__u32			status;		/* thread synchronous flags */
	__u32			cpu;		/* current CPU */
	int 			preempt_count;	/* 0 => preemptable, <0 => BUG */

	mm_segment_t		addr_limit;	
	struct restart_block    restart_block;
};
```
task指向对应的task_struct实例，exec_domain我们不涉及；
我们需要关注两个flags，一个是待觉信号标志TIF_SIGPENDING，一个是进程想要或应该调度时设置的标志TIF_NEED_RESCHED
cpu说明了当前进程在哪个CPU上执行
preempt_count用于内核抢占
addr_limit指定了进程可以使用虚拟地址的上限，restart_block用于实现信号机制，我们先不关注；

我们可以通过读取寄存器快速获取内核栈地址，从而快速获取thread_info实例的地址，从而得到我们想要信息，比如说当前task_struct、cpu、内核抢占计数等等；每个进程都有自己独立的内核栈，内核栈和进程时一一对应的关系；

Linux接下来会判断当前用户创建的进程数量是否已经超过资源限制，如果是则要返回错误；当然如果用户是root用户或者分配了特殊的权限，是可以跳过该检查的；

接下来就是复制进程的各个资源，由于dup_task_struct是完全复制父进程的task_struct实例，两个实例的所有地址（除了stack）都指向了相同的资源；
Linux会根据传入的标志位决定是共享还是复制父进程的资源，一般来说如果设置了CLONE_xyz的标志，那么子进程就会和父进程共享资源，我们需要做的就是给资源的引用计数加一，反之则要复制资源，新的资源引用计数是1；

接下来就是建立进程间关系，即配置task_struct的各个链表元素；如果当前是创建线程，则需要考虑更多情况，我们暂时不涉及；

### 4.3 总体架构
我们想要实现一个进程复制的机制，最简单的方法就是kmalloc(sizeof(struct task_struct))，然后memcpy；但是task_struct中的很多成员都是指针型变量，所以直接memcpy是不合适的；
在Linux的实现中，所有资源都可以根据CLONE_FLAG，选择与父进程共享还是创建一个父进程的副本，这也是我们要实现的机制。但是Linux的task_struct中有相当多的成员，而我们的task_struct只包含其中一部分，因此我们只关注和我们相关的资源如何复制，目前task_struct的定义如下：
```
struct thread_info {
	struct paging_4gb_chunk *page_directory;
	struct registers registers;
	struct task_struct *process;
	struct thread_info *next;
	struct thread_info *prev;
};

struct task_struct {
	uint16_t id;
	char filename[KERNEL_MAX_PATH];
	struct thread_info *task;
	struct process_allocation allocations[KERNEL_MAX_PROGRAM_ALLOCATIONS];

	PROCESS_FILETYPE filetype;
	union {
		void *ptr;
		struct elf_file *elf_file;
	};

	void *stack;
	uint32_t size;

	struct keyboard_buffer {
		char buffer[KERNEL_KEYBOARD_BUFFER_SIZE];
		int head;
		int tail;
		int size;
	} keyboard;

	struct process_argument argument;
	int res;
};
```
