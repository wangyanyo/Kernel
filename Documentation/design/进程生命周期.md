## 1. 摘要
当前代码的进程生命周期机制与Linux有所不同，因此实现Linux的标准进程生命周期管理；
**验收标准**：修改用户程序，通过fork、exec、exit、wait等系统调用维护进程生命周期，用户程序运行无问题；

## 2. 背景与问题
**我们为什么要这样做：**
我们的最终目的是，该内核可以直接替换Ubuntu的Linux内核正常使用，因此就需要保证系统调用的接口与行为与Linux保持一致；
**目前的问题：**
在当前代码中，通过一个system系统调用同时完成了创建新进程和执行程序两个动作，这个和Linux的标准处理方式由所不同。\
**Linux内核的标准方案：**
在Linux内核中，进程的生命周期是这样的：
1. 当前进程先通过fork系统调用复制出一个新的进程；
2. 执行exec系统调用运行新的程序，当前进程是新进程的父进程；
3. 新进程执行结束后，会执行exit系统调用，内核会回收该进程的所有资源，但是不会释放struct task_struct实例；
4. 直到父进程执行wait系统调用，确认子进程已经死亡并顺便回收struct task_struct实例；

## 3. 目标与非目标
### 目标
- 我们要重构当前的代码，实现Linux内核中标准的进程的层次关系和生命周期管理；
### 非目标
- 只实现进程生命周期管理机制，及其相关的科技树，不考虑其它的机制，不要陷入到Linux源代码的细节中；

## 整体方案设计
### 4.1 《深入Linux内核架构》笔记
进程有五种状态，运行、等待、睡眠、终止、僵尸；
1. 当调度器决定从该进程收回CPU资源时，该进程的状态会从“运行”变为“等待”；
2. 当调度器为该进程分配CPU时间后，该进程的状态会从“等待”变为“运行”；
3. 如果进程必须等待事件，则其状态从“运行”变为“睡眠”；
4. 睡眠进程等待的事件发生后，其状态从”睡眠“变为“等待”；
5. 进程终止执行后，进程状态变为“终止”；

但是还有一个特殊的僵尸状态，即子进程终止执行，发起exit系统调用，内核回收该进程的所有资源，但没有释放对应的task_struct实例，
这就是一个僵尸进程，父进程发起wait4系统调用可以确认子进程终止执行，并顺便释放子进程的task_struct实例；
也就是说，如果父进程不调用wait4系统调用的话，僵尸进程会稳定的存在于系统中，引入常驻内存问题；

Linux内核涉及进程和程序的所有算法都围绕一个名为task_struct的数据结构建立，task_struct是Linux内核最核心的数据结构之一；
我们只关注与我们当前项目相关的结构成员：
```
struct task_struct {
        volatile long state;    // 进程状态
        void *stack;            // 内核栈，内部还有一个thread_info
        
        long exit_state;                // 进程退出状态
        int exit_code;                  // 进程退出码

        unsigned did_exec:1;

        pid_t pid;

        // 进程间层次关系
        struct task_struct *parent;
        struct list_head children;
        struct list_head sibling;
};
```

在Linux内核中，有三种复制进程的方式：
1. fork: 重量级复制，它建立了父进程的一个完整副本，然后作为一个子进程执行；这样做有很多缺点，需要申请大量内存而且耗时很长，更关键的是，通过
   fork创建出的新进程大概率要执行一个新的程序，因此之前复制的大部分内容都失效了，尤其是复制了一整个内存空间都浪费了；但是Linux内核为fork
   引入了写时复制机制，大大减少了fork所需的时间和内存；
2. vfork: vfork创建了一个父进程的轻量级副本，执行vfork后，父进程会进入睡眠状态，直到子进程执行新程序；
3. clone: clone是fork的一个变体，用于创建线程，可以传入各种定制化的参数；

由于fork引入了写时复制技术，因此vfork在速度上不再有优势，更何况还有对父进程的限制，因此现在应该避免使用vfork；

在调用fork时，内核通常会对父进程的每个内存页，都为子进程创建一个副本，这有两个负面影响：
- 使用了大量内存
- 复制耗费了很长时间

但是这样做的收益甚微，创建子进程无非两种情况：
1、子进程和父进程并行执行，但是一个技术事实是，进程通常只使用内存页的一小部分，大部分复制的内存页子进程都不会访问；
2、子进程立即执行新的程序，复制的内存页将全部被丢弃；
也就是说，fork系统调用的复制是完全多余的，造成了内存和时间上的浪费；
因此引入的写时复制技术，父子进程可以随意读共享内存页，但是如果要写内存页，会触发中断并复制该内存页内容，然后再执行写操作，该过程父子进程都不感知；

执行进程复制的函数是do_fork函数，该函数的定义如下：
```
long do_fork(unsigned long clone_flag,
             unsigned long stack_start,
             struct pt_regs* regs,
             unsigned long stack_size,
             int __user *parent_tidptr,
             int __user *child_tidptr);
```
该函数的参数含义如下：
- clone_flag是一个标志集合，用来指定复制过程的一些属性。最低字节指定了在子进程终止时发给父进程的信号，其余高位字节保存了各种常数；
- stack_start是用户状态下栈的起始地址；
- regs是一个指向寄存器集合的指针，其中以原始形式保存了调用参数；struct pt_regs是一个特定于体系结构的数据结构；
- stack_size是用户状态下栈的大小；
- parent_tidptr和child_tidptr我们不关注；

为了避免后期大规模重构，项目的上层接口定义与Linux内核保持一致；
clone_flag一般传SIGCHLD，代表子进程终止后会向父进程传SIGCHLD信号，便于父进程执行wait4系统调用；
如果do_fork成功，会返回新进程的pid作为系统调用的结果返回，否则返回错误码；
